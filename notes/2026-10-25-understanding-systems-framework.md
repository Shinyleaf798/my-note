# 理解一个系统:三层追问 + 六步拆解

## 问题:会用,但讲不清

每天用 CI/CD,PR 变绿就合并,红了就去看日志 —— 这样用一年也不一定懂它。
被人问"你们的流水线是怎么设计的",才发现自己只知道按钮在哪,不知道它为什么长这样。

自己没搭过不是问题,**没理解**才是。下面两个工具,一个用来学,一个用来讲。

## 学:三层追问

每个技术都按三层问下去,大部分人停在第一层:

| 层次 | 问自己 | 例子(CI/CD) |
| --- | --- | --- |
| 是什么 | 由哪几步组成? | push → 测试 → 构建镜像 → 部署 |
| 为什么 | 去掉这一步会出什么问题? | 不跑测试,坏代码直接上线 |
| 取舍 | 还有别的做法吗?为什么没选? | 自动部署 vs 手动审批,各自的风险 |

第二层的问题可以反过来验证:**故意弄坏它。** 写一个会失败的测试,看 CI 怎么拦住;
换一个更差的配置,看指标怎么掉。亲眼见过一次失败,"为什么需要这一步"就不用背了。

## 讲:六步拆解

讲任何流水线或系统,都可以按这个顺序:

1. **触发** —— 什么事件让它开始?
2. **流程** —— 经过哪些步骤?每步产出什么?
3. **门槛** —— 哪一步失败会让整个流程停下?
4. **上线** —— 怎么部署?怎么确认部署成功?
5. **出事** —— 怎么回滚?谁会收到通知?
6. **为什么** —— 为什么这样设计?哪里可以改进?

前五步是描述,只有第六步体现理解。讲不出第六步,说明还停在三层追问的第一层。

## 例 1:CI/CD

一条常见的流水线按六步拆开:

| 步骤 | 内容 |
| --- | --- |
| 触发 | 开 PR、push 到 main |
| 流程 | lint → 类型检查 → 单元测试 → 构建 Docker 镜像 → 推到镜像仓库 |
| 门槛 | 任一检查失败,PR 不能合并 |
| 上线 | 先自动部署到 staging;production 需要手动审批 |
| 出事 | 回滚到上一个镜像 tag;失败通知到频道 |
| 为什么 | staging 先暴露环境相关的问题;审批防止误上线 |

第六步的"可以改进"往往是最好的切入点,比如:

- 部署后没有冒烟测试,靠人去点一下确认 → 加 `/health` 检查,返回版本号比对
- 镜像只打 `latest` → 同时打 commit sha,回滚时才知道回到哪个版本

## 例 2:RAG

RAG 一句话:**先从资料里检索相关片段,再让 LLM 只根据这些片段回答。**

六步对应过来:

| 步骤 | 内容 |
| --- | --- |
| 触发 | 离线:文档更新;在线:用户提问 |
| 流程 | 离线:切块 → embedding → 写入向量库。在线:问题 embedding → 取 top-k → 拼 prompt → LLM 回答 |
| 门槛 | 检索评测(hit@k、MRR)低于基线就不合并 |
| 上线 | 换 embedding 模型必须全量重建索引 |
| 出事 | 检索分数太低 → 不调 LLM,直接说"没有相关内容" |
| 为什么 | 见下表 |

"为什么"这一层,每个设计都对应一个取舍:

| 设计问题 | 取舍 |
| --- | --- |
| 为什么不把所有文档塞进 prompt? | 成本、上下文长度,无关内容还会干扰回答 |
| 块切多大? | 太大检索不准,太小丢上下文 —— 没有标准答案,用评测集实测 |
| 怎么知道检索变好了? | 固定评测集 + hit@k / MRR,每次改动都比较 |
| 怎么减少幻觉? | prompt 限定只用片段、要求标注引用、低分拒答 |
| 向量库和普通数据库的区别? | 按语义相近查,而不是关键字精确匹配;靠 HNSW 这类近似索引才够快 |
| pgvector 还是专用向量库? | 数据量小时 pgvector 够用,还能和业务数据放同一个库;规模大了再换 |

> **评测是"做过 RAG demo"和"做过 RAG 系统"的分界线。** 能做出能回答问题的 demo 很容易,
> 说得出"我怎么知道它变好了"才难。

## 一句话

**学的时候追问到取舍,讲的时候落到为什么。** 自己没搭过的系统也能讲清楚 —— 先说明自己的角色,
再按六步拆开,最后提一个改进点。
