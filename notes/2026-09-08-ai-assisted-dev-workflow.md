## 为什么需要这套流程

完全交给 AI 写代码很快，但容易变成"黑箱开发"——项目跑起来了，但说不清楚为什么这样设计、踩过什么坑。这套流程的目标是：**让 AI 做执行，但保留理解和决策记录**，这样每个项目完成后不仅有产出，还有可以写进 portfolio 的学习痕迹。

核心分工：
- **网页端 Claude**：负责规划、架构设计、复盘总结
- **Claude Code（IDE 内）**：负责按具体任务写代码

这套流程不针对某一类项目，网站、App、脚本工具、数据分析项目都适用，区别只在于第 1、3 步里具体讨论的内容不同。

## 完整流程

### 1. 在网页端 Claude 里先做完整规划

不要一上来就打开 IDE 让 AI 写代码。先在对话里定清楚：
- 需求范围（MVP 是什么，哪些功能先不做）
- 技术栈选型（及选型理由，而不只是选了什么）
- 核心数据结构 / 状态设计
- 主要接口或模块的边界划分

产出一份完整的项目说明文档。这一步的价值在于：自己先理解整体架构，之后看 AI 写的代码才有参照系，不会看不懂。

> **示例**：做一个记账 App 时，这一步产出了数据库表结构（`User` / `Category` / `Transaction`）和一份 API 接口清单（`/auth/*`、`/transactions/*`、`/stats/*`），并且明确了"金额用 Decimal 不用 Float"这类设计理由。

### 2. 初始化仓库，写好项目规则文件

建好仓库后，第一件事是写一份规则文件（例如 `CLAUDE.md`），把约定交代清楚：

```markdown
# 项目规则

## 技术栈
(按具体项目填写，例如：数据库 / 后端框架 / 前端框架 / 认证方式)

## 开发约定
- 每完成一个功能模块后，在 DECISIONS.md 中追加一条记录：
  做了什么 / 为什么这样设计 / 有什么替代方案被放弃了
- Commit message 必须说明改动原因，不只是描述改了什么
- 每个关键模块完成后附一句注释说明设计意图
```

这份文件相当于给 AI 定规矩，之后每次开新任务它都会先读这个，不用每次重复解释项目背景。

> **示例**：记账 App 项目里的一条 commit message 写的是"改用JWT而非session，因为要支持移动端无状态认证"——这种记录本身就是可以直接写进笔记的内容。

### 3. 把项目拆成具体的小任务

不要说"帮我做整个后端"，而是拆成可以独立验证完成与否的小任务，按顺序排好。任务粒度越小，越容易跟上并理解每一步在做什么。

> **示例**：记账 App 的后端被拆成了「建数据库 schema」→「写注册/登录接口」→「写 transactions 增删改查接口」→「写月度统计接口」四个独立任务，一次只推进一个。

### 4. 逐任务推进，每次都复盘理解

每次只丢一个任务给 AI。写完后不只是看能不能跑，还要用固定清单追问：

- 这段代码具体在做什么？
- 为什么选这种实现方式，而不是别的？
- 这里有什么坑或 trade-off？

复盘完，让 AI 往 `DECISIONS.md` 追加记录、写清楚原因的 commit，再进入下一个任务。

> **示例**：追问月度统计接口时发现，AI 选择在数据库层用 `GROUP BY` 聚合而不是把所有记录拿到前端再计算——这个"在哪一层做聚合"的取舍本身就是值得写进笔记的知识点。

### 5. 每个阶段结束做一次集成验证

比如某个模块全部写完后，先用工具（如 Postman）或简单脚本把功能真正跑一遍，确认逻辑没问题，再开始下一模块。避免等全部写完才发现某个环节接不上。

> **示例**：后端 API 全部完成后，先用 Postman 把每个接口单独跑一遍；等手机端也做完，再做一次手机端调用后端的端到端测试，而不是两边都写完才第一次联调。

### 6. 各部分分别部署上线

按项目的实际组成分别部署（比如后端/数据库上云、前端部署、客户端打包分发）。这一步经常会遇到环境变量、跨域、CI/CD 配置这些新问题，也值得记录。

> **示例**：记账 App 里，后端部署到 Render、网页部署到 Vercel、手机端通过 Expo EAS 打包，这个阶段本身就踩了环境变量配置的坑，值得单独写一条笔记。

### 7. 把整个过程转化成笔记

项目完成后，把 `DECISIONS.md` 和开发过程中的问答整理丢给 Claude，让它按笔记站需要的格式（frontmatter、分类、标签）转换成正式笔记，发布出来，并在对应的项目页面建关联条目。

> **示例**：这正是这篇笔记本身的来源——先用这套流程做了记账 App 的规划，再把过程中反复用到的方法论单独抽出来，写成一篇可复用的通用笔记。

## 小结

这套流程本质上是把"用 AI 写代码"这件事拆成了「规划 → 小任务执行 → 强制复盘 → 记录决策 → 验证 → 部署 → 转化产出」几个环节。多出来的成本主要在第 4 步的追问和第 2 步的日志维护，但换来的是一份可以直接支撑 portfolio 叙事的开发记录，而不只是一个能跑的项目。这套流程本身也是可迭代的——每用一次都可以回来更新这篇笔记，补充新发现的坑或者更好的做法。
