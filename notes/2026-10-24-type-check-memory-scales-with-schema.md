# 同一个 exit 137,这次程式码救不了——型别检查的内存随 schema 成长

> 前情:「一行型别签章吃掉 1GB——CI build 挂在 exit 137」(见文末「相关笔记」)。
> 那次是**一个签章**写坏了,用 `Pick<>` 窄化就解决。这次症状一模一样,但照那篇做**完全无效** ——
> 病因不同。

## 问题

CI build 又挂了,一样是 `exit 137`,一样没有任何编译错误。

照上一篇的诊断顺序走:先看 exit code(137 = 资源问题,不是程式写错)、确认本机跟 CI 做的是同一件事
(`.dockerignore` 排除了增量快取档,CI 永远冷编译)、回头找最近有没有新增「巨大型别的结构性比对」。

**找不到。** 那个模式已经一处都不剩了 —— 全部把 client 当参数传出去的呼叫端,签章都已经是
`Pick<>` 窄化过的。

然后才注意到:**这次的日志跟上次不一样。**

## 第一件事:两种 exit 137 要分开

```
FATAL ERROR: Ineffective mark-compacts near heap limit
Allocation failed - JavaScript heap out of memory
----- Native stack trace -----
```

上一次**没有这几行**,只有一个光秃秃的 exit code。差别很关键:

| 日志 | 实际发生什么 | 该怎么做 |
| --- | --- | --- |
| 只有 `exit 137`,一个字都没印 | 核心的 OOM killer 送了 SIGKILL,**实体记忆体**不够 | 调大堆上限**会更糟** |
| 有 `Ineffective mark-compacts near heap limit` | **V8 自己的堆上限**先到,进程自己喊停 | 调大堆上限**正是解法** |

V8 在 64 位元上不会无限长,它启动时按「看得到多少记忆体」自己挑一个上限。容器里这个上限常常只有
2 GB 左右 —— 哪怕宿主机还很空。所以会出现「机器明明有记忆体,V8 却先把自己掐死」。

> 补充:这次两种讯号同时出现 —— V8 印完 `FATAL ERROR`,正在印 native stack trace 时日志就断了,
> 而最终 exit code 是 137 而不是 abort 的 134。合理的解读是 V8 自己的上限先到,核心随后在它
> 收尾时补了一刀。而 CI 里两个 image 是**并行**建的,实体记忆体同时被另一个 build 吃着。
> 两件事都是真的,但**先发生的是 V8 的上限**,所以解法看前者。

## 为什么:型别也要占内存

这一段是上一篇没讲透的部分。

### 第 1 步:型别是编译期的物件

`tsc` 检查程式码时,会在内存里替**每一个型别**建一个物件:

```ts
const a = 1          // 建一个「number」
const b = [1, 2, 3]  // 建一个「number[]」
```

几个型别只占几 KB,无感。

### 第 2 步:泛型是模板,用一次印一张

```ts
type Box<T> = { value: T }

type A = Box<string>   // 内存里多一个型别物件
type B = Box<number>   // 再多一个
type C = Box<Date>     // 再多一个
```

`Box` 只写了一次,但**用了 3 次就有 3 个物件**躺在内存里。像影印机:模板只有一张,印出来的每一张
都要堆在桌上。

👉 关键:**同样的参数算过一次会被快取**。`Box<string>` 写十次,内存里还是一个。
花钱的是「**有多少种不同的组合**」,不是「写了几次」。这一点后面会反覆用到。

### 第 3 步:ORM 生成的模板非常大

现代 ORM 从 schema 产生一个 client,每张表一组 delegate,每个方法都是层层套叠的
conditional / mapped 型别。写一行:

```ts
db.item.findMany({
    where:   { status: 'PUBLISHED' },
    include: { sessions: true },
})
```

编译器必须算出「这行到底回传什么形状」。它不是算 1 个型别,而是一整串:
先算 `where` 能填哪些栏位 → 再算 `include` 展开成什么 → 再把两边拼成回传型别……

**一行这样的呼叫,可能印出几十到几百张。**

实测:ORM runtime 的那个 `.d.ts` 本身只有几千行模板,一次 build 却从它印出了**十五万个**型别物件。

### 第 4 步:这是乘法

```
上百张表  ×  每张表在程式码里被呼叫很多次  =  天文数字
```

实测一次 build 总共印出**八十多万个**型别物件。按「宣告在哪」归类:

| 宣告位置 | 占比 |
| --- | --- |
| ORM runtime + 生成码 | **约 27%** |
| query builder 的型别工具 | **约 10%** |
| `lib.es5.d.ts` 等标准库 | 约 10% |
| 其余 | 专案自己的程式码 |

### 第 5 步:`tsc` 跑完才一起丢

一次 build 从头到尾,所有印出来的型别都堆着不放,直到行程结束。所以是**累加**的,中途不会降。

### 第 6 步:query builder 是平行的第二条线

这条容易被忽略。生成码里还有一份「资料库目录」:

```ts
export type DB = {
    item:    Item;
    order:   Order;
    // ... 上百张表
};
```

而 query builder 的型别长这样:

```
SelectQueryBuilder< DB , 用到哪些表 , 会回传什么 >
         ↑
    整份上百张表的清单
```

**每一个查询物件,型别上都扛着整份 `DB`。** 为什么要扛?因为它得帮你抓错字:

```ts
qb.selectFrom('item as i')
  .innerJoin('order as o', 'o.item_id', 'i.id')
  .select(['i.name'])
```

`'o.item_id'` 只是一个**字串**。要判断它对不对,编译器必须:在清单里找 `order`(走过上百个项目)
→ 取出它所有栏位名 → 确认 `item_id` 在里面。**这中间每一步算出来的东西本身也是型别,也要存。**

而且链上每接一次就换一个新型别:

```ts
qb.selectFrom('item as i')              // SelectQueryBuilder<DB, 'i', {}>
  .innerJoin('order as o', ...)         // SelectQueryBuilder<DB, 'i' | 'o', {}>          ← 新的一张
  .select(['i.name'])                   // SelectQueryBuilder<DB, 'i' | 'o', { name }>   ← 又一张
```

专案里有几百处这样的查询起点,每一处的表组合和回传形状都不同 → **几乎都是全新的实例化,不能共用。**

ORM 和 query builder 是**两条互不相干的线**(各自从同一份 schema 生成),但**同一个原因**让两条都涨。

### 第 7 步:所以「越来越大」是这样来的

上一次修好之后的两周多,schema 的表数长了**约两成**。

多出来的不只是那几份模板 —— 是**新增的程式码又去呼叫它们**,每一处呼叫又印一批。两边相乘,
两周就把余裕吃光了。

👉 **这是本篇的核心:型别检查的内存成本,会随 schema 的规模线性(甚至超线性)成长,
而且全 codebase 均匀分摊。**

## 量测:四个方向,三个无效

既然日志指向某个具体位置,直觉是去改那段程式码。`tsc --generateTrace` 也很配合地指出了
**整个 build 最贵的单一宣告** —— 一条两百多行的 query builder 链,被重复检查 47 次。

四个方向全部实测过:

| 做法 | 省下 |
| --- | --- |
| 把链上十几个 `.select()` 合并成一个 | **0 MB** |
| 把回传型别截断成手写的 interface(`$castTo`) | **9 MB** |
| **把那两百多行的查询整段删光**(功能全废,纯探测) | **37 MB** |
| 调高 builder 的堆上限(一行设定) | 需要多少给多少 |

**把最贵的那段整个删掉也只省 37 MB** —— 而缺口比这更大。

为什么?回到第 2 步那个 👉:**TypeScript 会快取**。那条链再长、再贵,它用到的型别种类早就被
别处的几百个查询实例化过了。删掉它,那些型别照样存在。

同理:
- 合并 `.select()` 省 0,因为重复写同一个形状本来就免费
- 截断回传型别只省 9 MB,因为被换掉的只是第三个型别参数,`DB` 那份清单还在,而且**另外几百个
  查询完全没动到**

👉 **最贵的宣告 ≠ 值得改的地方。** trace 告诉你钱花在哪,但没告诉你省不省得下来。

## 量测方法本身的坑

这次最大的收获其实在这里。上一篇的结论是「先量再改」,这一篇要补:**量错一样会推错。**

### 坑 1:峰值 heap 的噪音比你要测的差异还大

用 `node --trace-gc` 抓最大堆用量,同一份程式码两次跑出来可以差 **±90 MB**。
而我要分辨的差异是 20–50 MB —— **根本量不出来**,还白白得出过「某某改动省了 54 MB」的错误结论。

原因:堆的峰值取决于 GC 什么时候心血来潮,不是「真正需要多少」。堆上限给得宽,V8 就让垃圾多堆一会儿。

### 坑 2:改用「能通过的最低堆上限」,但要注意二分的容忍度

```bash
# 二分搜寻:哪个 --max-old-space-size 刚好还能编过
NODE_OPTIONS="--max-old-space-size=$mid" <真正的 build 指令>
```

pass/fail 是确定性的,没有噪音。但我第一版脚本的终止条件写成 `gt 100`,**解析度只有 ±100 MB** ——
三个不同版本全部报同一个数字,我差点当成「它们真的一样」。收到 16 MB 之后才分得开:

```
2,068 MB   原状
2,059 MB   截断回传型别
2,031 MB   整段查询删光
```

### 坑 3:本机过,不代表 CI 过

本机那份只要 2,068 MB 就能编过,**低于** CI 容器的 2,092 MB 上限 —— 也就是说**本机根本复现不出
这个失败**。架构、libc、node 版本的差异就足以造成 1–3% 的落差,而当时的余裕只剩 1%。

所以本机的绝对数字不能拿来判断「CI 会不会过」,只能当**相对比较**用。

### 坑 4:量你要量的那个指令

一开始图快用 `tsc --noEmit`,但 CI 跑的是会 emit 的完整 build。emit 要额外的内存。
差异不大,但没有理由不量对的那个。

### 坑 5:先量天花板,再决定要不要动手

最省时间的一步,是**先做一次「把它整个删掉」的探测**,看这条路最多能省多少。
37 MB 这个数字一出来,后面所有重写的方案就都不用考虑了 —— 省下的是几小时的白工。

## 如何解决

把堆上限明确设死在 **build 阶段**:

```dockerfile
FROM deps AS builder
COPY . .
# 型别检查会把全专案的查询对着上百张表验证一遍,需求随 schema 成长,
# 已经超过 Node 预设的 ~2 GB(exit 137)。只给 build 阶段;runtime 阶段另起,不受影响。
ENV NODE_OPTIONS=--max-old-space-size=4096
RUN <build 指令>
```

三个要点:

1. **只放 build 阶段。** 型别在编译后会被整个抹掉 —— 产出的 JS 里一个型别痕迹都没有,跑起来的
   服务完全不知道它们存在。production 容器一点都不会变大。
2. **调高上限不等于会用掉那么多。** V8 按需成长。原本冲到 2,092 就死,给它 4,096 之后实际用
   2,120 就收工 —— 多吃的实体记忆体只有几十 MB,不是多出来的 2 GB。
3. **什么时候不能这样做:** 如果日志里**只有** exit 137、没有 V8 的 heap limit 讯息,那是核心杀的,
   实体记忆体才是瓶颈 —— 这时调高上限只会让它死得更快。先分辨,再动手。

## 小总结

**跟某个 ORM 没有必然关系。**

> 型别检查的内存成本,随「schema 有多少表」× 「多少程式码在用它们」成长。
> 到了某个点,**没有任何一段程式码能改到达标** —— 因为成本是全 codebase 均匀分摊的,
> 不集中在任何一处。

**两次 exit 137 的对照:**

| | 上一篇 | 这一篇 |
| --- | --- | --- |
| 日志 | 只有 exit code | 多了 V8 的 heap limit 讯息 |
| 病因 | 一个签章写坏(局部) | 型别总量随 schema 成长(全域) |
| 解法 | `Pick<>` 窄化参数 | 调高 build 阶段的堆上限 |
| 程式码能解吗 | 能,而且省 ~1 GB | **不能,天花板只有 37 MB** |

**带走四句话:**

- **同一个 exit code 可以有完全相反的解法** —— 分辨点是日志里有没有 V8 自己的讯息
- **量测工具本身会骗你** —— 峰值 heap 有 ±90 MB 噪音,二分的容忍度会让不同的东西看起来一样
- **最贵的宣告不等于值得改的地方** —— 因为型别会快取,删掉它别处照样会把那些型别印出来
- **动手之前先量天花板** —— 一次「整个删掉」的探测,省掉几小时的白工

最后:上一篇的教训是「量错了就会建议错」。这一篇是它的下半句 ——
**量对了,也可能发现这件事根本不该从程式码下手。**
